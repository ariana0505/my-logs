## PUNTO DE PARTIDA

Necesito saber qué es un archivo, cómo guardarlo y qué es un repositorio. Git versiona archivos dentro del repositorio. GitHub guarda una copia remota, pero Git funciona localmente sin GitHub. Al clonar, obtengo una copia local y normalmente un remoto llamado origin.

---

## DE EDITAR UN ARCHIVO A GUARDAR UNA VERSIÓN

Un cambio puede pasar por tres lugares:

1. Carpeta de trabajo: edito y guardo el archivo. `git diff` muestra los cambios que aún no he preparado.
2. Área de preparación: `git add <archivo>` selecciona la versión actual para el próximo commit. `git diff --staged` muestra esa selección.
3. Historial: `git commit -m "mensaje"` registra lo preparado en un commit local. `git log --oneline` permite ver el historial.

`git status` muestra el estado de los archivos; no modifica ni guarda nada. Si edito un archivo después de `git add`, esa edición puede quedar sin preparar aunque la versión anterior esté preparada. Por eso consulto `git status` y ambos diffs antes del commit.

---

## LO QUE APRENDÍ

Editar, preparar y confirmar son acciones diferentes. `git add` no publica el cambio ni crea un commit. `git commit` tampoco lo sube a GitHub: para enviar los commits al remoto se usa `git push`. Git compara el contenido actual con el registrado. Si escribo una errata y la corrijo antes de confirmar, y el archivo vuelve a ser idéntico al último commit, `git status` ya no muestra ese cambio.

---

## EJEMPLO PARA PRACTICAR Y EXPLICAR

Después de añadir una frase a `README.md`:

```bash
git status
git diff
git diff --staged
```

La frase debería aparecer en `git diff` y no en `git diff --staged`. Después:

```bash
git add README.md
git status
git diff
git diff --staged
git commit -m "docs: explicar los estados de un cambio"
git log --oneline
```

Antes del commit, la frase debería aparecer en `git diff --staged`; después, el commit en `git log --oneline`. Son resultados esperados; falta anotar las salidas reales.
